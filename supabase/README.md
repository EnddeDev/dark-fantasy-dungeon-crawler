# Переезд на Supabase (внешний BaaS)

Клиент уже умеет работать с любым бэкендом, который отвечает по контракту из `docs/online.md`:
адрес задаётся переменной `VITE_API_URL`, типы лежат в `src/net/protocol.ts`.

## Что нужно от проекта

1. URL проекта: `https://<project>.supabase.co`.
2. Публичный anon-ключ (он не секретный, но и не пароль — в Git его обычно не коммитят).
3. Аккаунт Supabase Auth можно не использовать: игра входит по логину и паролю через свой API,
   а Supabase Auth требует почту. Проще держать Edge Function `api`, которая повторяет наши маршруты.

## Шаги

1. Создать проект и выполнить `supabase/schema.sql` в SQL Editor.
2. Развернуть Edge Function `api` (Deno) либо поднять сервер из папки `server/` на любом хостинге
   и направить её на Postgres. Логика маршрутов — `server/api.ts`.
3. Указать в сборке `VITE_API_URL=https://<project>.supabase.co/functions/v1/api`.
4. Включить RLS: таблицы читаются только через функцию, наружу отдаются лишь безопасные проекции.

## Что обязательно перенести на сторону базы

Эти операции должны быть атомарными, иначе возможны дубли предметов и золота:

- `market.buy` — списание золота покупателя, начисление продавцу, передача предмета, статус лота;
- `market.cancel` / `trades.decline|cancel` — возврат предметов из эскроу;
- `trades.counter` — эскроу встречного набора;
- `trades.accept` — одновременная передача двух наборов;
- `duels.action` — запись состояния боя и проверка `deadline` (20 секунд на ход).

В `schema.sql` для этого оставлены комментарии-заготовки; при переносе их стоит оформить как
`create function ... security definer` и вызывать через `rpc()`.
